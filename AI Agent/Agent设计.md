##### Multi-Agent系统和单Agent系统的优缺点？什么时候选用
Multi-Agent是把复杂任务按照某种维度拆解给多个Agent协作完成
- **优点：**
	- 节省主Agent的上下文窗口。使用多个子智能体来处理问题，最后把又价值的部分汇总给主Agent，这样主Agent的上下文窗口就不会被海量信息给污染
	- 并行探索，效率更高
	- 擅长并行任务，多个智能体互不干扰
- **缺点**：
	- Token消耗量大
	- 如果需要所有智能体共享同一个上下文（例如实时编辑）或者智能体之间存在大量互相依赖关系，则不适合。因为目前智能体之间的协调能力还不够成熟，可能会引入噪音
##### Multi-Agent的设计思路
1. **先判断任务适不适合Multi-Agent**
	- 任务链长？任务是否可以并行？不同子任务是否需要不同能力？
2. **拆分Agent**
	按照职责边界来拆，每个agent只负责一件事
	- 层级式：会设计一个Planner负责任务拆解，然后由多个Executor去执行具体任务，比如检索、推理或者计算，最后由一个Aggregator汇总结果
	- 流水线式：agent A的输入是agent B的输出，适合有明确先后顺序的任务
3. **Agent之间通信协作方式**
	- **结构化的 JSON 消息**：每个 agent 输出标准格式，供下游 agent 解析使用
	- **共享内存**：所有 agent 共享一个上下文空间，比如一个 memory store，所有中间结果都写进去，其他 agent 可以读取
	- **消息队列（MQ）**：使用消息队列让agent之间异步通信
##### 每个Agent是否都需要大模型调用
根据任务复杂度来选择，只有需要语义理解或者内容生成的Agent才调用LLM，分类Agent和工具Agent（查DB、调API）则不需要LLM
##### 多Agent如何拆分？trade-off是什么？
**拆分维度**：
- 按功能（理解，规划，执行，验证）
- 按领域（不同业务线）
**Trade-off**：
- 细粒度拆分：
	- 更灵活度，可控性更强
	- 复杂度和延迟也会增加
- 粗粒度拆分：
	- 系统简单，好维护
	- 单点prompt复杂
##### pipeline中如果其中一个agent出错了，产生错误输出，下游agent该如何处理
以传递JSON格式为例，可以做的优化有：
1. 提示工程 + few-shot示例，强制输出JSON，并配合例子
2. 结构化输出。开启模型的structured output或json schema功能
3. 后处理。正则表达式校验 + 修复；或工程上常用pydantic + 模型重试的方法修复
