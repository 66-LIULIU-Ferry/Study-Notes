## 定义
- Retrieval Augmented Generation，检索增强生成，给模型输入资料，让模型基于资料来回答
- 因为RAG成本低，上手快，知识更新方便且答案可追溯，所以RAG适合知识密集、更新频繁、需要可追溯的场景。

## RAG核心流程
![[截屏2026-05-08 16.20.01.png]]
##### 1. Ingest：把数据导入
把数据接入系统
##### 2. Chunk：把长文档切成小块
**Chunk太大/太小的问题**
- Chunk太大：检索不够精确，还容易超出上下文限制
- Chunk太小：语义不完整，上下文丢失
**Chunk实际切分策略**
1. 先根据文档类型选策略：
	- **层级切分**：文档有明切结构且层级明显用，例如技术文档，法律合同等有明确章节结构的；
	- **语义切分**：有明确结构但是没有层级的用，例如新闻博客
	- **固定大小**：文档没有明切结构，例如用户评论，客服对话
2. **固定大小切分**
	通常256-512 token，同时加overlap，让相邻chunk共享一段文字，防止一句关键信息被切分
3. **语义切分**
	用小模型判断语义边界（比如段落结束、话题转换），在自然断点处切分而不是强行按字数切
4. **层级切分**
	按标题层级切，H1 下面的内容作为一个大 Chunk，H2 下面的作为子 Chunk，形成层级结构
##### 3. Embed：把文字变成向量
这串数字编码了这段文字的语义信息，意思相近的文字，向量在空间中的距离也近
##### 4. Index：存进向量数据库
向量数据库专门存向量，做相似度搜索——给一个向量，找出距离最近的 N 个
##### 5. Retrieve：检索相关内容
当用户进行提问时：
1. 把用户问题转换成向量
2. 拿这个向量去向量数据库搜索，找出最相似的几个文档快
##### 6. Answer：大模型生成回答
把检索到的内容和用户问题打包给大模型，让大模型基于检索出的资料生成答案

## RAG用户提问链路（当用户发起提问后，会经历哪些流程？）
##### 1. 用户输入
用户在前端界面输入自然语言问题，通过WebSocket / SSE 协议发送到后端
- **WebSocket**：全双工通信协议，适合实时双向交互
- **SSE**：服务器单向推送，适合流式输出场景
##### 2. 会话记忆加载
根据 `conversationId` 和 `userId` 加载历史对话记录，与当前问题合并，形成**完整上下文窗口**。
- **多轮对话管理**：LLM 本身无状态，需要手动维护历史消息
- **Context Window 管理**：历史过长需做截断/摘要，避免超出 Token 限制
- **会话隔离**：通过 conversationId 区分不同用户会话
##### 3. 查询改写与拆分
对用户问题进行**改写优化**（补全指代、明确表达），并识别是否为**复合问题**进行拆分，生成子问题列表。
- **Query Rewriting**：解决指代不明、省略语等问题
- **Query Decomposition**：将复杂问题拆解为多个子问题，提升召回精度
- **HyDE（假设性文档嵌入）**：有时也在此阶段生成假设答案以辅助检索
##### 4. 意图解析
对每个子问题并行进行**意图分类**，输出多个意图类型及置信度排序：

| 意图类型     | 说明           |
| -------- | ------------ |
| KB意图     | 去知识库检索文档     |
| MCP意图    | 调用外部工具 / API |
| SYSTEM意图 | LLM直接回答      |
- **意图分类（Intent Classification）**：NLU 核心任务，可用 LLM 或分类模型实现
- **并行执行**：多个子问题同时处理，降低整体延迟
- **置信度打分**：支持多意图共存，按概率排序处理
##### 5. 歧义引导判断
计算歧义分值，若**超过阈值**则判定问题存在歧义，进入边界确认流程，返回**引导式澄清提示**让用户重新选择。
- **歧义检测**：模型判断问题表述是否不够明确
- **短路设计（Short-circuit）**：提前终止流程，避免无效检索消耗资源
- **主动澄清策略**：提升用户体验，减少错误答案
##### 6. 系统直答判断
若**所有子问题的意图均为 SYSTEM 类型**（通用/闲聊），则无需检索外部数据，直接调用 LLM 流式输出答案。
- **意图路由**：根据意图决定是否走检索链路
- **直接生成 vs RAG**：通用问题直接用 LLM，专业/私域问题才走 RAG
- **流式输出（Streaming）**：LLM 边生成边推送，提升响应体验
##### 7. 多通道检索
核心检索阶段，分为两条并行通道：
###### 7a：知识库检索通道（KB）
- **多通道检索（MultiChannel）**：同时在多个知识库检索
- **TopK 文档召回**：返回相关度最高的 K 个文档片段
- **格式化为结构化上下文**
###### 7b：MCP 工具调用通道
- **LLM 提取工具参数**：从问题中解析调用参数
- **并行调用 MCP 工具**：获取实时结构化数据
- 结果存入 `mcpContext`
**知识点：**
- **向量检索（Vector Search）**：将文本 Embedding 后做语义相似度匹配
- **混合检索**：向量检索 + BM25 关键词检索结合
- **MCP（Model Context Protocol）**：Anthropic 提出的 LLM 工具调用标准协议
- **RetrievalContext 合并**：将 `kbContext` 和 `mcpContext` 融合为统一上下文
- **空检索短路（出口 C）**：若检索结果为空，直接返回"未检索到相关内容"
##### 8. Prompt组装 + 流式输出
根据意图组合选择**模板类型**（纯 KB / 纯 MCP / KB+MCP 混合），组装最终消息序列：
```
系统提示词
+ MCP 动态数据
+ KB 文档内容
+ 历史对话
+ 用户问题
```
最终通过 **SSE/Streaming** 流式推送到前端。
**知识点：**
- **Prompt Engineering**：系统提示词设计直接影响输出质量
- **RAG Prompt 结构**：将检索内容注入 Prompt 的标准范式
- **Token 预算管理**：各部分内容需控制长度，防止超出上下文窗口
- **流式传输**：SSE 逐 Token 推送，实现打字机效果

##### Embedding 和 向量匹配
- Embedding：把文字的语义翻译为数字
- 向量匹配：计算两段文字语义的相似程度，也就是计算两个向量之间的距离
##### RAG系统中，超过了模型上下文窗口，有哪些解决思路
- **chunk压缩**：对检索出来的结果先进行一步压缩
- **top-k选择**：根据token预算动态决定放几个chunk
- **rerank**：重排序，先用向量检索"粗筛"出较多候选，再用更精准的模型"精排"，只保留最相关的chunk输入
> [!NOTE] Notes
> - 超出上下文窗口：RAG会把检索到的文档片段（chunks）塞进prompt，但模型有上下文长度限制，检索结果太多就装不下了
> - 向量检索：把文字embedding后变成数字，用数字之间的距离来衡量语义相似度，找出意思最接近的文档
##### RAG相比于Claude Code等目前的各种agent，他的优势和劣势在哪里
- **RAG的优势**：
	- **可拓展性更强**。新数据源只需要embeding入库，而agent需重新全量上下文检索
	- **信息可控**。向量检索方式和结果是确定的，而agent依赖模型决策和语义理解，有随机性
	- **实现成本简单**。RAG的pipeline非常标准化，并且对llm的token消耗更少
- **RAG的劣势**：
	- **检索精确度**。RAG基于向量匹配，精确度不如agent的工具调用方式
	- **数据依赖**。RAG的效果强依赖于数据的质量，而agent通过实时搜索不会有这个问题
	- **复杂任务不适用**。RAG的效果来自于静态检索，对于多步推理的复杂任务不适应
> [!NOTE] RAG 和 Coding Agent 的区别
> - RAG：用户问题 → 检索文档 → 塞进Prompt → 模型回答
> - Coding Agent：用户问题 → 模型自己决定 → 调用工具/搜索/执行代码 → 回答
