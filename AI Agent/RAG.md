## 定义
- Retrieval Augmented Generation，检索增强生成，给模型输入资料，让模型基于资料来回答
- 因为RAG成本低，上手快，知识更新方便且答案可追溯，所以RAG适合知识密集、更新频繁、需要可追溯的场景。

## RAG核心流程
![[截屏2026-05-08 16.20.01.png]]
##### 1. Ingest：把数据导入
把数据接入系统
##### 2. Chunk：把长文档切成小块
**Chunk太大/太小的问题**
- Chunk太大：检索不够精确，还容易超出上下文限制
- Chunk太小：语义不完整，上下文丢失
**Chunk实际切分策略**
1. 先根据文档类型选策略：
	- **层级切分**：文档有明切结构且层级明显用，例如技术文档，法律合同等有明确章节结构的；
	- **语义切分**：有明确结构但是没有层级的用，例如新闻博客
	- **固定大小**：文档没有明切结构，例如用户评论，客服对话
2. **固定大小切分**
	通常256-512 token，同时加overlap，让相邻chunk共享一段文字，防止一句关键信息被切分
3. **语义切分**
	用小模型判断语义边界（比如段落结束、话题转换），在自然断点处切分而不是强行按字数切
4. **层级切分**
	按标题层级切，H1 下面的内容作为一个大 Chunk，H2 下面的作为子 Chunk，形成层级结构
##### 3. Embed：把文字变成向量
这串数字编码了这段文字的语义信息，意思相近的文字，向量在空间中的距离也近
##### 4. Index：存进向量数据库
向量数据库专门存向量，做相似度搜索——给一个向量，找出距离最近的 N 个
##### 5. Retrieve：检索相关内容
当用户进行提问时：
1. 把用户问题转换成向量
2. 拿这个向量去向量数据库搜索，找出最相似的几个文档快
##### 6. Answer：大模型生成回答
把检索到的内容和用户问题打包给大模型，让大模型基于检索出的资料生成答案

##### Embedding 和 向量匹配
- Embedding：把文字的语义翻译为数字
- 向量匹配：计算两段文字语义的相似程度，也就是计算两个向量之间的距离
##### RAG系统中，超过了模型上下文窗口，有哪些解决思路
- **chunk压缩**：对检索出来的结果先进行一步压缩
- **top-k选择**：根据token预算动态决定放几个chunk
- **rerank**：重排序，先用向量检索"粗筛"出较多候选，再用更精准的模型"精排"，只保留最相关的chunk输入
> [!NOTE] Notes
> - 超出上下文窗口：RAG会把检索到的文档片段（chunks）塞进prompt，但模型有上下文长度限制，检索结果太多就装不下了
> - 向量检索：把文字embedding后变成数字，用数字之间的距离来衡量语义相似度，找出意思最接近的文档
##### RAG相比于Claude Code等目前的各种agent，他的优势和劣势在哪里
- **RAG的优势**：
	- **可拓展性更强**。新数据源只需要embeding入库，而agent需重新全量上下文检索
	- **信息可控**。向量检索方式和结果是确定的，而agent依赖模型决策和语义理解，有随机性
	- **实现成本简单**。RAG的pipeline非常标准化，并且对llm的token消耗更少
- **RAG的劣势**：
	- **检索精确度**。RAG基于向量匹配，精确度不如agent的工具调用方式
	- **数据依赖**。RAG的效果强依赖于数据的质量，而agent通过实时搜索不会有这个问题
	- **复杂任务不适用**。RAG的效果来自于静态检索，对于多步推理的复杂任务不适应
> [!NOTE] RAG 和 Coding Agent 的区别
> - RAG：用户问题 → 检索文档 → 塞进Prompt → 模型回答
> - Coding Agent：用户问题 → 模型自己决定 → 调用工具/搜索/执行代码 → 回答
