
## 基础知识
---
##### 1. 查询语句执行流程
1. **客户端**发送SQL查询语句到MySQL服务器
2. **MySQL服务器**连接器开始处理这个请求，跟客户端建立连接、获取权限、管理连接
3. （MySQL 8.0后已经不存在）建立连接后，**MySQL服务器的查询缓存组件**会检查是否又缓存的查询。如果有，则直接返回给客户端；如果没有，进入下一步
	- ==Query Cache存在的问题==：
		1）命中条件严格，SQL语句需要完全一样，命中率低
		2）只要表有更新，相关缓存全部失效，维护成本高
		3）使用全局锁，严重影响并发性能
4. **解析器**开始对SQL语句进行解析，检查语句是否符合SQL语法规则，确保引用的数据库、表和列都在，并处理SQL语句中的名称解析和权限验证
5. **优化器**负责确定SQL语句的执行计划，包括选择使用哪些索引，以及决定表之间的连接顺序等。优化器会尝试找出最高效的方式来执行查询
6. **执行器**会调用**存储引擎的API**来进行数据读写
7. **客户端**收到查询结果，完成查询请求
##### 2. 常用命令
###### 2.1 数据库
- 创建数据库：`CREATE DATABASE database_name;`
- 删除数据库：`DROP DATABASE database_name;`
- 选择数据库：`USE DATABASE database_name;`
##### 3. 数据表的主键、外键和索引都是什么
- 主键：是用来唯一表示一行数据的字段
- 外键：是用来建立表与表之间关联关系的字段
- 索引：用于提高查询效率，相当于给数据建立一个快速查询的结构

## 存储引擎
---
**Innodb**（5.5以后默认）**MyISAM**（5.5之前）、**Memory**（存储在内存）  
- Innodb支持事务、行级锁和外键，适合高并发场景
- MyISAM不支持事务和外键，支持表级锁，适合读多写少的场景
- Memory不支持外键也无主键，适合临时表
- Innodb是聚簇索引，索引树聚在一块；MyISAM是非聚簇  

## 日志
---
##### 1. MySQL日志文件都有哪些
1. **错误日志（Error Log）**
	记录 MySQL 服务器启动、运行或停止时出现的问题。  
2. **慢查询日志（Slow Query Log）**
	记录执行时间超过 long_query_time 值的所有 SQL 语句。这个时间值是可配置的，默认情况下，慢查询日志功能是关闭的。可以用来识别和优化慢 SQL。 
3. **一般查询日志（General Query Log）**
	记录所有 MySQL 服务器的连接信息及所有的 SQL 语句，不论这些语句是否修改了数据。  
4. **二进制日志（Binary Log）**
	记录了所有修改数据库状态的 SQL 语句，以及每个语句的执行时间，如 INSERT、UPDATE、DELETE 等，但不包括 SELECT 和 SHOW 这类的操作。 
	- 物理日志，会在磁盘上记录下数据库的所有修改操作，以便进行数据恢复和主从复制
	- 当发生数据丢失时，binlog可以将数据库恢复到特点的时间点，主服务器（master）上的二进制日志可以从被服务器（slave）读取，从而实现数据同步
	- 默认没启动，需要去配置文件配置参数
	- 用于==主从复制（保证多台机器数据一致）==

以及两个 InnoDB 存储引擎特有的日志文件：  
1. **重做日志（Redo Log）**
	物理日志，记录了对于 InnoDB 表物理级别的修改（记录数据本身的变化而非操作语句），主要用于==崩溃恢复==。  
2. **回滚日志（Undo Log，或者叫事务日志）**
	记录数据被修改前的值，用于事务的回滚。==支持事务回滚，可以用来实现 MVCC，即多版本并发控制==。
##### 2. undo log 和 redo log的区别
###### 2.1 数据操作过程
- **缓冲池（buffer pool）**：主内存中的一个区域，里面可以缓存磁盘上经常操作的真实数据，在执行增删查改操作时，先操作缓冲池中的数据（如果缓冲池中没有数据，则从磁盘加载并缓存），以一定频率刷新到磁盘，从而减少磁盘IO，加快处理速度
- **数据页（page）**：数据的基本存储单位，每个页的大小默认为16KB，页中存储的是行数据
 ![[Pasted image 20260415010847.png]]
 但是当服务器宕机时，如果内存中的数据还未同步到磁盘中，内存中的数据可能会丢失，违背了事务的持久化特性，因此引入日志文件 redo log
> [!NOTE] 脏数据页
> 内存里已经被修改，但还没写回磁盘的数据页
###### 2.2 redo log
- 重做日志，记录的是事务提交时数据页的物理修改，是**用来实现事务的持久性**。
- 该日志文件由两部分组成：**重做日志缓冲（redo log buffer）以及重做日志文件（redo log file）**，前者是在内存中，后者在磁盘中。当事务提交之后会把所有修改信息都存到该日志文件中，用于在刷新脏页到磁盘、发生错误时，进行数据恢复使用。
 ![[Pasted image 20260415011123.png]]
 - 当buffer pool发生变化时，redo log会记录变化，同时也会同步到redo log file。所以当脏页数据同步失败之后，数据库会从日志中进行恢复
###### 2.3 undo log
- 回滚日志，用于记录数据被修改前的信息，作用包含两个：**提供回滚** 和 **MVCC（多版本并发控制）**
- undo log 和 redo log 记录物理日志不一样，它是**逻辑日志**
- 可以认为当 delete 一条记录时，undo log 中会记录一条对应的 insert 记录，反之亦然。
- 当 update 一条记录时，它记录一条对应相反的 update 记录。当执行 rollback 时，就可以从 undo log 中的逻辑记录读取到相应的内容并进行回滚。
- ==**undo log 可以实现事务的一致性和原子性**==
###### 2.4 面试回答
- redo log：记录的是数据页的**物理变化**，服务宕机可用来同步数据
- undo log：记录的是**逻辑日志**，当事务回滚时，通过逆操作恢复原来的数据
- redo log 保证了事务的持久性，undo log 保证了事务的原子性和一致性
##### 3. Binlog 和 redolog的区别
- 记录的内容不同：binlog记录的时关于一个事务的具体操作内容，即逻辑日志；而redolog是关于每个页的更改的物理情况
- 写入的时间不同：binlog仅在事务提交时（commit）进行，也就是只写入磁盘一次；但redolog在执行过程中是持续地写
- 写入的方式也不相同：redo log 是循环写入和擦除，新数据会覆盖旧数据；bin log 是追加写入，不会覆盖已经写的文件。
##### 4. redolog和binlog的两阶段提交
###### 4.1 为什么需要两阶段提交
两种日志处于不同的层次，binlog位于MySQL Server层，redolog位于InnoDB存储引擎层，当进行对应的SQL操作的时候都会进行日志的记录，那么先写谁后写谁就会成为问题，因此引入两阶段提交（不同于分布式事务中的两阶段提交）
###### 4.2 什么是二阶段提交
将一个事务的提交过程拆分为准备阶段和提交阶段两个步骤，确保redolog和binlog的日志原子性，要么二者都完整的持久化到磁盘中，要么二者都不持久化，这种机制是为了保证数据一致性而存在的
###### 4.3 完整执行过程
- **第一步：执行SQL语句阶段**
	1. 事务开启后，执行SQL语句，先把redolog写入内存中的log buffer
	2. 修改buffer pool中的数据页（在内存中修改）
	3. 再把binlog写入内存（是否落盘由参数控制）
- **第二步：执行COMMIT指令阶段**
	1. InnoDB把redo log持久化到磁盘
	2. 此时redo log的状态标记为`prepare`
	3. 然后binlog也开始持久化到磁盘
- **第三步：Server确认binlog落盘**
	1. MySQL Server确认binlog持久化之后，向InnoDB发送“可以提交的信号”
	2. InnoDB将redolog的状态从`prepare` -> `commit`
- **第四步：事务完成**
	1. InnoDB释放锁，回滚段等资源
	2. 向客户端返回执行成功的响应
	3. 整个事务完成

##### 1. 慢查询
###### 1.1 慢查询定义
表象：页面加载过慢、接口压测响应时间过长（超过1s）
- 聚合查询
- 多表查询
- 表数据量过大查询
- 深度分页查询
###### 1.2 方法
1. **开源工具**
	- 调试工具：Arthas
	- 运维工具：Prometheus，Skywalking
2. **MySQL自带慢工具**
	慢查询日志记录了所有执行时间超过指定参数（`long_query_time`，单位：秒，默认10s）的所有SQL语句的日志。如果需要开启慢查询，需要在MySQL的配置文件（/etc/my.cnf）种配置如下信息：
```C++
	# 开启MySQL慢日志开关
	slow_query_log = 1
	# 设置慢日志的时间为2秒，SQL语句执行时间超过2秒，就会被视为慢日志，记录慢查询日志
	long_query_time = 2
```
###### 1.3 面试回答
- 如何定位慢查询
	1. 首先介绍当时产生问题的场景：我们当时一个接口测试的时候非常慢，压测的结果大概为5秒钟
	2. 我们系统中当时采用了运维工具（Skywalking），可以监测出哪个接口，最终因为是sql的问题
	3. 在mysql中开启了慢日志查询，我们设置的值就是2秒，一旦sql执行超过2秒就会记录到日志中（调试阶段）
> [!NOTE] 接口压测
> 1. 接口：指的是后端API接口，也就是前端或客户端调用的HTTP接口，例如：GET /api/user/list?page=1&size=10
> 2. 压测（压力测试）：模拟大量用户同时请求这个接口，来测试它的性能。采用JMeter模拟并发用户请求该接口
##### 2. 如果SQL语句执行很慢，如何分析
可以采用 `EXPLAIN` 或者 `DESC` 命令获取MySQL如何执行SELECT语句的信息
![[Pasted image 20260413230611.png]]
- `possible_keys`：当前sql可能会使用到的索引
- `key`：当前sql实际命中的索引
- `key_len`：索引占用的大小
	- 通过 key 和 key_len 查看是否可能会命中索引
- `Extra`：额外优化建议
	![[Pasted image 20260413230811.png]]
- `type`：sql访问方式，性能由好到差为NULL，system，const，eq_ref，range，index，all
	- **all**：全表扫描，从头扫到尾，最差
	- **index**：扫了整个索引树，比all略好但还是很慢
	- **range**：在索引上扫一个范围，比如 age > 18
	- **ref**：通过普通索引，找到匹配的几行
	- **eq_ref**：通过唯一索引，精确找到一行
	- **const**：通过主键/唯一索引，直接找到一行，极快
	- **system**：表只有一行数据，特殊情况
	- **NULL**：不用查表，直接返回结果
###### 2.1 面试回答
可以采用MySQL自带的分析工具 EXPLAIN
- 通过 key 和 key_len 检查是否命中了索引（索引本身是否有失效的情况）
- 通过 type 字段查看sql是否有进一步的优化空间，是否存在全索引扫描或全盘扫描
- 通过extra建议判断，是否出现了回表的情况，如果出现了，可以尝试添加索引或者返回字段来修复
##### 3. 索引为什么会加快查询速度？
- 数据库文件是存储在磁盘上的，磁盘 I/O 是数据库操作中最耗时的部分之一。没有索引时，数据库会进行全表扫描（Sequential Scan），这意味着它必须读取表中的每一行数据来查找匹配的行（时间效率为 O(n)）。当表的数据量非常大时，就会导致大量的磁盘 I/O 操作。  
- 索引就是MySQL在表数据之外，**额外维护的一个有序目录，目录里的每一项指向真实数据的位置**，查询时通过目录快速定位，不用扫全表，从而大大减少了磁盘 I/O 操作的次数。  
- MySQL 的 InnoDB 存储引擎默认使用 B+ 树来作为索引的数据结构，而 B+ 树的查询效率非常高，时间复杂度为 O(logN)。
- 索引文件相较于数据库文件，体积小得多，查到索引之后再映射到数据库记录，查询效率就会高很多。
##### 4. 索引分类
1. 按功能
	- **主键索引**: 表中每行数据唯一标识的索引，强调列值的唯一性和非空性 `PRIMARY KEY`
	- **唯一索引**: 保证数据列中每行数据的唯一性，但允许有空值 `UNIQUE`
	- **普通索引**: 基本的索引类型，用于加速查询 `INDEX`
	- **全文索引**：特定于文本数据的索引，用于提高文本搜索的效率 `FULLTEXT INDEX`
2. 按数据结构
	- **B+树索引**：最常见的索引类型，一种将索引值按照一定的算法，存入一个树形的数据结构中（二叉树），每次查询都从树的根节点开始，一次遍历叶子节点，找到对应的值。查询效率是 O(logN)。  
	- **Hash 索引**：基于哈希表的索引，查询效率可以达到 O(1)，但是只适合 = 和 in 查询，不适合范围查询。  
> InnoDB 并不提供直接创建哈希索引的选项，因为 B+ 树索引能够很好地支持范围查询和等值查询，满足了大多数数据库操作的需要。不过，InnoDB 存储引擎内部使用了一种名为“自适应哈希索引”的技术。自适应哈希索引并不是由用户显式创建的，而是 InnoDB 根据数据访问的模式自动建立和管理的。当 InnoDB 发现某个索引被频繁访问时，会在内存中创建一个哈希索引，以加速对这个索引的访问。
 3. 按存储位置
	- **聚簇索引**：聚簇索引的叶子节点保存了一行记录的所有列信息。也就是说，聚簇索引的叶子节点中，包含了一个完整的记录行。  
	- **非聚簇索引**：它的叶子节点只包含一个主键值，通过非聚簇索引查找记录要先找到主键，然后通过主键再到聚簇索引中找到对应的记录行，这个过程被称为回表。
##### 5. 创建索引
建表时创建
```sql
CREATE TABLE users (
    id INT PRIMARY KEY,                    -- 主键索引
    id_card VARCHAR(18) UNIQUE,            -- 唯一索引
    name VARCHAR(50),
    age INT,
    city VARCHAR(50),
    INDEX idx_name (name),                 -- 普通索引
    INDEX idx_name_age (name, age, city)   -- 联合索引
);
```
建表后单独创建
```sql
CREATE INDEX idx_name ON users(name);              -- 普通索引
CREATE UNIQUE INDEX idx_card ON users(id_card);    -- 唯一索引
CREATE INDEX idx_name_age ON users(name, age);     -- 联合索引
```
###### 5.1 索引创建原则
1. ==数据量较大，且查询比较频繁的表==
	- 单表超过10万数据，主要目的是提升用户体验
2. ==常作为查询条件、排序、分组的字段==
3. 字段内容区分度高
4. 对于字符串类型的字段，如果内容较长，使用前缀索引
5. ==尽量联合索引==
	- 减少单列索引，查询时，联合索引很多时候可以覆盖索引，节省存储空间，避免回表，提高查询效率
```sql
-- 单列索引（分别建）
CREATE INDEX idx_name ON user(name);
CREATE INDEX idx_age  ON user(age);

-- 联合索引（合并建）
CREATE INDEX idx_name_age ON user(name, age);
```
6.  ==要控制索引的数量==
7. 如果所有列不能存储NULL值，在创建表时使用NOT NULL约束
	- 减少优化器思考时间，让它更高效
> [!NOTE] 回表
> 用普通索引查询时，索引里的数据不够用，需要**拿着主键id再去查一次主键索引**，才能拿到完整数据的过程。
###### 5.2 什么情况下索引会失效
索引失效的情况有多种，可以适当思考一下，说一些自己遇到过的，不要直接背诵面试题
1. **违反最左前缀法则**
	如果索引了多列，要遵守最左前缀法则，指的是查询从索引的最左前列开始，并且不跳过索引中间的列，否则可能会导致索引失效
2. **范围查询右边的列，不能使用索引**
	例如：`select * from tb_seller where name = '小米' and status > '1' and address = '北京市'`，这种情况adress的条件就会失效
3. **不要在索引列上进行运算操作，否则索引将失效**
	例如：`select * from tb_seller where substring(name, 3, 2) = '科技'`
4. **字符串不加单引号**
	例如：`select * from tb_seller where name = '科技' and status = 0`，这种情况下status会失效
5. **以%开头的模糊查询，索引失效；如果是尾部模糊，则索引不会失效**
##### 6. 索引的底层数据结构
###### 6.1 B树
- 因为索引位于硬盘中，硬盘访问次数与树高相关，为了减少硬盘访问次数，加快数据访问，所以我们引入B树
- 相比二叉树和红黑树，B数的节点元素个数可以是多个
- B树有以下特征：
	1. **平衡**：所有叶节点都在同一层
	2. **有序**：节点内元素是有序的
	3. **多路**：对于m阶B树的结点
		- 最多：m个分支，m-1个元素
		- 最少：
			- 根节点：2个分支，1个元素
			- 其它节点：[m/2]个分支，[m/2]-1个元素
###### 6.2 B+树
MySQL默认使用的是B+树，该结构是对B树进行的改进
- 叶节点包含所有元素，并从小到大通过指针连接成链表。因此我们可以通过头指针进行顺序查询
- 叶节点的每个元素，即关键字，都包含着一个指针，指向数据文件中某行元素的位置
- B树和B+树的时间复杂度都是O(log n)
###### 6.3 B+树和B树的区别
![[Pasted image 20260428204224.png]]
- **B树**：
	- 所有结点的关键字都有直接指向对应记录的指针
	- B树中m个分支有m-1个关键字
	- B树仅支持随机查找，不支持**顺序查找**
- **B+树**：
	- **叶结点包含关键字及指向对应记录的指针，非叶结点只作索引**
	- B+树中m个分支有m个关键字
	- B+树兼顾顺序查找、随机查找和范围查找
###### 6.4 InnoDB选择B+树的原因
1. **更高效的磁盘 IO**：因为它减少了磁盘寻道时间和页的加载次数（B树节点大小通常和页大小对齐）。	
> 	MySQL从磁盘读取数据，是以页为单位。在B树里，每个节点 = key + data，节点体积大，一页里能放的节点少，树更高；而B+树非叶节点只能存key，体积小，树更矮，IO更少，所以磁盘寻道次数就少
2. **支持范围查询**：与 B 树相比，B+树的叶子节点通过指针连接成一个链表，这使得范围查询变得非常高效。在 B+树上执行范围查询可以简单地从范围的起始点开始，然后沿着链表向后遍历，直到结束点。  
3. **查询性能稳定**：B+树的所有查找操作都要查到叶子节点，这使得所有的查询操作**都有着相同的访问深度**，因此查询性能非常稳定。不像某些其他数据结构，如 B 树，其查询性能因为数据存在所有的节点上导致深度不一致，性能不稳定。
##### 7. 聚簇索引
什么是聚簇索引，什么是二级索引（非聚集索引），什么是回表
###### 7.1 聚集和非聚集索引
![[Pasted image 20260414155306.png]]
- **聚集索引：数据本身的组织方式（必须有）**
	表中的行是按照索引的顺序存储的，表中的实际数据行和键值之间存在物理排序关系。因此每个表只能由一个聚集索引。
	- 索引选取规则：
		1. 如果存在主键，主键索引就是聚集索引
		2. 如果不存在主键，将使用第一个唯一（UNIQUE）索引作为聚集索引
		3. 如果没有合适的唯一索引，则InnoDB会自动生成一个rowid作为隐藏的聚集索引
- **二级索引：建立在聚集索引之上的额外查询入口（可选）**
	- 索引和数据是分开存储的，索引中的键值指向数据的实际存储位置。因此，非聚簇索引也被称为二级索引或辅助索引
###### 7.2 回表查询
当使用非聚簇索引查找数据时，数据库会进行两步操作：  
  1. **查找索引**：数据库首先会查找非聚簇索引，找到索引键值对应的索引项。这个索引项包含了数据行在磁盘上的位置信息。  
2. **读取数据**：然后，数据库会根据位置信息，去磁盘上读取相应的数据行。  
这个过程也被称为“回表”，因为数据库需要先查找索引，然后再根据索引回到数据表中去查找实际的数据。因此，使用非聚簇索引查找数据通常比使用聚簇索引要慢，当然，如果索引所在的数据页已经被加载到内存中，那么非聚簇索引的查找速度也可以非常快。

###### 7.3 面试问题
1. **什么是聚簇索引什么是非聚簇索引？** 
	- 聚簇索引（聚集索引）：数据与索引放到一块，B+树的叶子节点保存了整行数据，有且只有一个
	- 非聚簇索引（二级索引）：数据与索引分开存储，B+树的叶子节点保存对应的主键，可以有多个 
2. **知道什么是回表查询嘛？** 
	- 通过二级索引找到对应的主键值，到聚集索引中查找整行数据，这个过程就是回表

1. **表的设计优化**

	- 设置合适的字符串类型（char 和 varchar）：char 定长效率高，varchar 可变长度，效率稍低

3. **SQL语句优化**
	- SELECT 语句务必指明字段名称（避免直接使用 `select *`）
	- SQL 语句要避免造成索引失效的写法、
	- 尽量用 `union all` 代替 `union`，`union` 会多一次过滤，效率低
		- `union`自动去除重复行，而`union all`会保留所有行，所以`union all`没有额外的去重操作，性能更好
	- 避免在 where 子句中对字段进行表达式操作
		- 会导致索引失败，被迫进行全表扫描
	- Join 优化：能用 `inner join` 就不用 `left join` / `right join`；如必须使用，一定要以小表为驱动。内连接会对两个表进行优化，优先把小表放到外边、大表放到里边；`left join` 或 `right join` 强制固定了驱动顺序，优化器无法自由调整
		- `innerjoin`：两者取交集，会自动选择小表驱动大表进行优化
		- `leftjoin`：左表全部+右表匹配部分
		- `rightjoin`：右表全部 + 左表匹配部分

## 事务
---
##### 1. 什么是事务（Transaction）
事务时一组操作的集合，它是一个不可分割的工作单位，事务会把所有的操作作为一个整体一起向系统提交或撤销操作请求，即**这些操作要么同时成功，要么同时失败**
##### 2. 事务的四个特征
ACID
- **原子性（Atomicity）**：事务是不可分割的最小操作单元，要么全部成功，要么全部失败。
- **一致性（Consistency）**：事务完成时，必须使所有的数据都保持一致状态。
- **隔离性（Isolation）**：数据库系统提供的隔离机制，保证事务在不受外部并发操作影响的独立环境下运行。
- **持久性（Durability）**：事务一旦提交或回滚，它对数据库中的数据的改变就是永久的。
##### 3. 并发事务带来的问题
###### 3.1 脏读
一个事务读到另外一个事务还没有提交的数据
###### 3.2 不可重复读
- 一个事务先后读取同一条记录，但是两次读取的数据不同
- 主要发生在两次事务先后读取过程中，有其它事务对数据库进行了操作	
###### 3.3 幻读
事务A查询一个范围，事务B往里插入/删除数据并提交，事务A再查同一范围，结果集不一样了（前后行数不一样）
	![[Pasted image 20260415002626.png]]
##### 4. 解决并发事务问题：对事务进行隔离
事务隔离级别越高，数据越安全，但是性能越低。串行化虽然能解决所有问题，但是操作就无法并行了，性能差，所以基本上都选择默认隔离级别，即可重复读
![[Pasted image 20260428215834.png]]
1. **读未提交**  
	读未提交是最低的隔离级别，在这个级别，当前事务可以读取未被其他事务提交的数据，以至于会出现“脏读”、“不可重复读”和“幻读”的问题。  
2. **读已提交**  
	当前事务只能读取已经被其他事务提交的数据，可以避免“脏读”现象。但不可重复读和幻读问题仍然存在。  
3. **可重复读**  
	==确保在同一事务中多次读取相同记录的结果是一致的==，即使其他事务对这条记录进行了修改，也不会影响到当前事务，是 MySQL 默认的隔离级别。  
4. **串行化**  
	最高的隔离级别，通过强制事务串行执行来避免并发问题，可以解决“脏读”、“不可重复读”和“幻读”问题。但会导致大量的超时和锁竞争问题。
##### 5. 保证事务的隔离性：MVCC + 锁
- **排他锁**，如果一个事务获取了一个数据行的排他锁，其它事务就不能再获得该行得其它锁
- **MVCC**：多版本并发控制
##### 6. MVCC                                      
- Multi-Version Concurrency Control，多版本并发控制。指维护一个数据的多个版本，使得读写操作没有冲突
- MVCC的具体实现，主要依赖于数据库记录中的**隐式字段**、**undo log日志**、**readView**
###### 5.1 隐式字段
![[Pasted image 20260415012533.png]]
###### 5.2 undo log日志和其版本链
![[Pasted image 20260415013150.png]]
不同事务或者相同事务对同一记录进行修改，会导致该记录的undo log生成一条记录版本链表，头部式最新的旧记录，尾部是最早的旧记录
###### 5.3 read view
- ReadView（读视图）是**快照读** SQL 执行时 MVCC 提取数据的依据，记录并维护系统当前活跃的事务（未提交的）id。
	- **当前读**
		读取的是记录的**最新版本**，读取时还要保证其他并发事务不能修改当前记录，**会对读取的记录进行加锁**。对于我们日常的操作，如：select ... lock in share mode（共享锁），select ... for update、update、insert、delete（排他锁）都是一种当前读。
	- **快照读**
		简单的 select（不加锁）就是快照读，快照读，读取的是记录数据的可见版本，**有可能是历史数据**，**不加锁**，是非阻塞读。
		- Read Committed：每次 select，都生成一个快照读。
		- Repeatable Read：开启事务后第一个 select 语句才是快照读的地方。
- **ReadView中包含了四个核心字段：**
	1. `m_ids`：当前活跃的事务ID集合
	2. `min_trx_id`：最小活跃事务ID
	3. `max_trx_id`：预分配事务ID，当前最大事务ID+1（因为事务ID是自增的）
	4. `creator_trx_id`：当一个事务执行快照读时，MySQL 会为它创建一个 ReadView，而 `creator_trx_id` 就是创建这个 ReadView 的事务的 ID
- **版本链数据访问规则**
	**trx_id**：代表是当前事务ID。
	1. `trx_id == creator_trx_id`？**可以访问该版本** → 成立，说明数据是当前这个事务更改的。
	2. `trx_id < min_trx_id`？**可以访问该版本** → 成立，说明数据已经提交了。
	3. `trx_id > max_trx_id`？**不可以访问该版本** → 成立，说明该事务是在 ReadView 生成后才开启。
	4. `min_trx_id <= trx_id <= max_trx_id`？**如果 trx_id 不在 m_ids 中是可以访问该版本的*** → 成立，说明数据已经提交。
- **不同的隔离级别，生成 ReadView 的时机不同：**
	- `READ COMMITTED`：在事务中每一次执行快照读时生成 ReadView。
	- `REPEATABLE READ`：仅在事务中第一次执行快照读时生成 ReadView，后续复用该 ReadView
###### 5.4 面试问题
**Q：好的，事务中的隔离性是如何保证的呢？（你解释一下MVCC）**
MySQL 中的多版本并发控制。指维护一个数据的多个版本，使得读写操作没有冲突。
- **隐藏字段**：
	- trx_id（事务id），记录每一次操作的事务id，是自增的
	- roll_pointer（回滚指针），指向上一个版本的事务版本记录地址
- **undo log**：
	- 回滚日志，存储老版本数据
	- 版本链：多个事务并行操作某一行记录，记录不同事务修改数据的版本，通过 roll_pointer 指针形成一个链表
- **readView 解决的是一个事务查询选择版本的问题**
	- 根据 readView 的匹配规则和当前的一些事务id判断该访问那个版本的数据
	- 不同的隔离级别快照读是不一样的，最终的访问的结果不一样
		- RC：每一次执行快照读时生成 ReadView
	    - RR：仅在事务中第一次执行快照读时生成 ReadView，后续复用

## 锁
---
##### 1. 锁的粒度
1. **全局锁**：锁住整个库
2. **表锁**：锁住整张表。开销小，并发低
3. **行锁**：锁住单行数据。开销大，并发高
##### 2. 悲观锁 和 乐观锁
1. 悲观锁：写多读少
2. 乐观锁：读多写少
##### 3. 共享锁 和 排他锁
1. 共享锁：多个事务可以同时读取同一资源。读读共享，读写互斥
2. 排他锁：独占资源，其它事务无法读写。
##### 4. 意向锁
- 本质：表级锁，但服务于行锁
- 机制：当事务获取行锁时，InnoDB自动为其加上意向锁
- 作用：当事务想加表锁时，无需遍历所有行，只需检查意向锁，极大提升效率
- 分类：意向共享锁，意向排他锁
##### 5. InnoDB行锁的实现
###### 5.1 记录锁
记录锁就是直接锁定某行记录
###### 5.2 间隙锁
间隙锁(Gap Locks) 的间隙指的是两个记录之间逻辑上尚未填入数据的部分,是一个左开右开空间。
###### 5.3 临键锁
临键指的是间隙加上它右边的记录组成的左开右闭区间。临键锁就是记录锁(Record Locks)和间隙锁(Gap Locks)的结合，即除了锁住记录本身，还要再锁住索引之间的间隙。
> [!NOTE] 防止幻读
> 间隙锁和临建锁是为了解决幻读的问题，MVCC解决的是执行读操作时的幻读情况，而锁是防止写操作造成的幻读

> DML：Data Manipulation Language，用来操作数据库内容的，也就是增删改数据

3. slave 重做中继日志中的事件，将改变反映它自己的数据。
